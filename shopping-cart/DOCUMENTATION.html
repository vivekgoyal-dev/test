What this is

A shopping cart backend built as seven Spring Boot applications. Three roles, JWT login through an API gateway, Feign for service-to-service calls, validation on every request body, and AOP logging in each service. There is no frontend: everything is driven from Swagger or Postman.

It is running and tested. An end to end script walks registration, login, listing a product, filling a cart, checkout, shipping, and every rejection in between: 19 checks, 0 failures. Every request and response on this page was captured from that running system, not written by hand.

USER

Registers, keeps a profile, browses, fills a cart, places orders, sees their own orders and cancels one that has not shipped.

SHOPOWNER

Everything a user can do, plus listing products they own, and shipping the orders placed for those products.

ADMIN

Sees every user, profile and order. Can delete any product. Cannot place an order.

Two rules run through the whole system and are worth holding in mind while reading the rest: a shopowner can only touch their own products, and a user only ever sees their own cart, profile and orders. Both are enforced from the identity in the token, never from a value the caller sends.

How it fits together

Read it in three layers.

One door. A client only ever talks to :8080. The gateway matches the path against a route table, checks the token, checks the role, and forwards. A request that fails either check never reaches a service, which is why the services carry no security code of their own.

Identity travels as headers. The gateway converts the token into X-User-Id and X-User-Role and sets them on the forwarded request. Every controller behind the gateway reads those, so no service parses a JWT and there is one copy of the signing secret to keep safe rather than six.

Two services call other services, both over Feign. cart-service asks product-service for a price. order-service reads the cart at checkout and asks product-service who owns each product, so a shopowner can later be shown the orders for their own goods. Nothing else crosses a boundary.

The honest limit of this design

The services trust those headers, so they are only as protected as the gateway in front of them. Running locally you can still call :8083 directly and claim to be anyone. That is the normal starting point for a project this size, and the fix when it matters is to stop exposing service ports and let only the gateway reach them.

The user record is split so nothing is duplicated. auth-service holds the userId, email, password hash and role. profile-service holds the same userId with no password, plus name, phone, gender and date of birth. The userId comes from the token, so neither service ever has to ask the other for anything.

The eight folders

Every service has the same eight folders under com.shoppingcart.<service>, so anyone who has read one service can navigate all of them.

  • controller reads the headers, calls one service method, wraps the result in a ResponseEntity. An if doing business logic belongs one layer down.
  • service holds every rule and is the only layer that throws a business exception.
  • dto is separate from model on purpose. It is how a password is accepted at registration and never appears in a response.
  • exception holds one @RestControllerAdvice, so a failure is clean JSON with the right status rather than a stack trace.

There is no ninth folder, and that decided two placements: auth-service's SecurityConfig and JwtUtil live in config/, and the Feign client interfaces live in service/ beside the classes that use them.

Not built, on purpose

Refresh tokens, password reset, email verification, logout and token blacklisting. Each is a real feature and each can be added without changing anything above.

Feign, for service to service

Feign turns an HTTP call into an interface. You declare the call and Spring writes the client; the service name is resolved through Eureka, so no port appears anywhere in the code.

Calling it reads like a method call:

Two things make it work: spring-cloud-starter-openfeign in the pom, and @EnableFeignClients on the main class. Only cart-service and order-service need either.

order-service uses it twice at checkout, and the second one is easy to miss the point of. It reads the cart from cart-service rather than accepting a cart posted by the client, and asks product-service who owns each product, so that GET /orders/received can later show a shopowner exactly the orders for their own goods.

Validation, exceptions and the controller

These three are one flow. The controller only receives, validation rejects bad input before any rule runs, and the advice turns whatever is thrown into one JSON shape.

The annotations do nothing on their own. @Valid on the parameter is what triggers them:

Every service has the same advice, catching three things: a validation failure becomes a 400 listing each bad field, an ApiException becomes whatever status it carries, and anything unplanned becomes a 500 with a generic message so a stack trace never reaches a caller.

The ownership rule

Every product stores the ownerId taken from the token when it was created. Edit and delete compare that against the caller. Without this check, any shopowner with a valid token could rewrite or delete the entire catalog, which is the kind of thing that is very cheap to add now and very awkward to retrofit.

Proven in the test run: shopowner 2 editing shopowner 1's product gives 403, deleting it gives 403, and shopowner 1 editing their own gives 200. An ADMIN skips the check on delete, which is the one intentional exception.

Running it on Windows, in Eclipse

Seven projects, started in one particular order. Do these once and the rest is a button.

1

Install the tools

JDK 17 or newer, Eclipse with Spring Tools 4 (Help › Eclipse Marketplace, search Spring Tools), and MySQL 8 (the Community installer, choosing Server only is enough). Note the root password you set during the MySQL install: you will need it in step 3.

2

Install Lombok into Eclipse

This one catches everyone. Lombok generates the getters and setters at compile time, and Eclipse needs a small agent before its editor can see them. Without it the code builds fine with Maven while the editor shows hundreds of red errors like getPrice() is undefined.

Find lombok.jar under C:\Users\<you>\.m2\repository\org\projectlombok\lombok\, then in a command prompt:

java -jar lombok.jar

Click Install / Update, point it at your Eclipse folder, then restart Eclipse.

3

Create the five schemas

Open MySQL Workbench, or the MySQL Command Line Client, and run:

CREATE DATABASE shopcart_auth;
CREATE DATABASE shopcart_profile;
CREATE DATABASE shopcart_product;
CREATE DATABASE shopcart_cart;
CREATE DATABASE shopcart_order;

One schema per service, which is what keeps them independent: product-service physically cannot join onto the orders table.

Each service reads its password from an environment variable. Set it once for the machine, then restart Eclipse so it picks it up:

setx DB_PASSWORD "your-mysql-root-password"

If you would rather not, put the password directly in each application.yml instead, but then do not commit those files anywhere public.

4

Import the projects

File › Import › Maven › Existing Maven Projects, point it at the shopping-cart folder, and tick all seven. Eclipse downloads the dependencies on first import, which takes a few minutes.

If a project shows errors afterwards, right-click it and choose Maven › Update Project.

5

Start them, discovery-server first

Right-click a project and choose Run As › Spring Boot App. Order matters only for the first one:

  1. discovery-server, then wait until localhost:8761 loads
  2. auth-service, profile-service, product-service, cart-service, order-service, in any order
  3. api-gateway last

Open the Boot Dashboard (Window › Show View › Other › Boot Dashboard) and you can select all seven and start or stop them together from then on.

Give it about 30 seconds, then check localhost:8761. All six applications should be listed. Cross-service calls do not work until they are.

6

Use it

Everything goes through http://localhost:8080. Start here:

POST http://localhost:8080/auth/register
{"email":"you@example.com","password":"secret123","role":"SHOPOWNER"}

POST http://localhost:8080/auth/login
{"email":"you@example.com","password":"secret123"}

Copy the token from the login response. In Postman put it under Authorization › Bearer Token, and every later call carries it automatically.

Each service also has its own Swagger page, useful for seeing one service in isolation: http://localhost:8083/swagger-ui.html for products. Note that Swagger talks to the service directly and so bypasses the gateway, which means no role checks and no X-User-Id header. For anything involving a logged-in user, use Postman against :8080.

When something does not work

Port 8081 was already in useAnother program has the port, or a previous run never stopped. Stop it in the Boot Dashboard, or change server.port in that service's application.yml. Nothing else needs editing, because the gateway finds services by name through Eureka rather than by port.
getPrice() is undefined, and hundreds of similar errorsLombok is not installed into Eclipse. Step 2 above, and restart Eclipse afterwards.
Access denied for user 'root'@'localhost'The DB_PASSWORD environment variable is not set, or Eclipse was not restarted after setting it. Check with echo %DB_PASSWORD% in a fresh command prompt.
Unknown database 'shopcart_cart'Step 3 was skipped or only partly run. Re-run the five CREATE DATABASE statements.
503 Service Unavailable from the gatewayThe target service is not running, or has not registered yet. Check localhost:8761: registration takes about 30 seconds after a service starts.
401 on every call, including ones that should workThe token is missing, expired (24 hours), or was pasted with a line break in it. Log in again and copy the whole token value.
403 when you expected it to workThe role is wrong for that endpoint. Check the role column in the endpoint tables above. A USER cannot list products, and a SHOPOWNER cannot read /orders.
400 with "required request header X-User-Id is not present"You called a service port directly instead of going through the gateway. Use :8080.

Deliberately not built

Listed so nobody assumes it is there: any wallet or payment, so orders are cash on delivery. Refresh tokens, password reset, email verification and logout. Product images. Ratings and reviews. Stock levels, so an order can be placed for something that is out of stock. A config server and centralised logging.

Each can be added without changing the seven projects, which is the point of stopping here.
