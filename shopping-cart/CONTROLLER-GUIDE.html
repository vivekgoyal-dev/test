Writing a Controller

The one class that receives web requests. What each line does, the four ways to get information out of a request, and a template to copy.

Part 1

What a controller is for

A controller is the class that receives requests from outside. When someone sends GET /products, a method in a controller runs.

Its job is deliberately small. Four steps, always the same:

1. Receive

Take the address, the JSON, and any headers.

2. Call one service method

Hand the work to the service class.

3. Wrap the answer

Put the result in a ResponseEntity with a status code.

4. Return it

Spring turns it into JSON and sends it back.

The rule to remember

A controller contains no thinking. No calculations, no database, no if deciding what is allowed. If you find yourself writing an if about business rules, that code belongs in the service class instead.

A good controller method is usually one line long.

Part 2

The top of the class, line by line

This is the real start of ProductController from the project.

@RestController
@RequestMapping("/products")
public class ProductController {

    private final ProductService service;

    public ProductController(ProductService service) {
        this.service = service;
    }
1@RestController tells Spring this class handles web requests, and that whatever a method returns should be turned into JSON.
2@RequestMapping("/products") puts /products in front of every address in this class. It saves repeating it on every method.
5The service is stored in a field. This is the class that does the real work.
7The constructor takes the service as a parameter. You never write new ProductService() anywhere. Spring sees the constructor, creates the service, and passes it in for you.

That last point has a name

It is called dependency injection. It means: do not build the things you need, ask for them, and let Spring hand them over. It is why Spring code has so few new keywords in it.

Part 3

One method per endpoint

Each thing the outside world can ask for is one method, labelled with the kind of request it answers.

LabelAnswers
@GetMappingGET, for reading
@PostMappingPOST, for creating
@PutMappingPUT, for updating
@DeleteMappingDELETE, for removing

Whatever is inside the brackets is added after the class address:

@RequestMapping("/products")     on the class
@GetMapping("/my")               on the method
                                 answers:  GET /products/my

@GetMapping                      no brackets at all
                                 answers:  GET /products

Two methods can share an address if their labels differ. @GetMapping and @PostMapping with no brackets both live at /products, and Spring picks the right one based on how the request was sent.

Part 4

The four ways to get information in

This is the part worth learning properly. A request can carry information in four different places, and each has its own label.

@PathVariable

Part of the address itself. Used for "which one".

GET /products/8

@GetMapping("/{productId}")
getById(@PathVariable Long productId)

@RequestParam

After a ? in the address. Used for extra options.

PUT /cart/items/8?quantity=3

@PutMapping("/items/{productId}")
update(@RequestParam int quantity)

@RequestBody

The JSON sent with the request. Used when creating or updating something.

POST /products
{ "productName": "Mouse",
  "price": 1299 }

add(@RequestBody ProductDto dto)

@RequestHeader

Extra information attached to the request. We use it for who is calling.

X-User-Id: 19

add(@RequestHeader("X-User-Id")
    Long ownerId)

The names have to match. With @PathVariable, the method parameter must be named the same as the word in the curly brackets:

@GetMapping("/{productId}")
public ResponseEntity<ProductDto> getById(@PathVariable Long productId) {
                    same word --^                              ^-- and here

If the names differ, Spring cannot work out which is which and the request fails. If you want them to differ, say so: @PathVariable("productId") Long id.

Why we never take the user id from the address

Notice that no endpoint in this project looks like /cart/{userId}. The user id always arrives in the X-User-Id header, put there by the gateway after it checked the token.

If it came from the address, anyone could type someone else's number and read their basket. A value in the address is chosen by the caller. A value in that header was decided by the gateway from a signed token, and the caller cannot fake it.

Part 5

Sending the answer back

Every method returns a ResponseEntity. That is just the answer plus the status code you want to send with it.

return ResponseEntity.ok(service.getAll());
// 200, with the list as JSON

return ResponseEntity.status(HttpStatus.CREATED).body(service.add(dto, ownerId));
// 201, with the new product as JSON

return ResponseEntity.noContent().build();
// 204, nothing in the body. Used after a delete

The type in the angle brackets says what the body will contain:

ResponseEntity<ProductDto>         one product
ResponseEntity<List<ProductDto>>   a list of products
ResponseEntity<Void>               nothing at all

You could return the object directly, without ResponseEntity, and Spring would send 200. We use ResponseEntity everywhere so that creating something can answer 201 Created rather than 200, which is the correct code and costs nothing.

What about errors?

Nothing. The controller never handles errors. If a product does not exist, the service throws an exception, and a separate class turns it into a tidy 404. There are no try/catch blocks in any controller in this project.

Part 6

Checking what was sent

The rules about what is acceptable live on the DTO class, next to each field:

public class ProductDto {

    @NotBlank(message = "product name is required")
    private String productName;

    @Positive(message = "price must be greater than 0")
    private double price;
}

But they only run if the controller asks for them, with @Valid:

public ResponseEntity<ProductDto> add(@Valid @RequestBody ProductDto dto) {

Forgetting @Valid is the single most common mistake here. The annotations on the DTO look right, the code compiles, and nothing is ever checked. A blank name sails straight through into the database.

With it in place, sending a blank name produces this automatically:

{
  "status": 400,
  "message": "validation failed",
  "errors": { "productName": "product name is required" },
  "timestamp": "2026-09-10T00:07:10"
}

Part 7

A complete real method, explained

This is add from ProductController, exactly as it is in the project.

@PostMapping
public ResponseEntity<ProductDto> add(@RequestHeader("X-User-Id") Long ownerId,
                                      @Valid @RequestBody ProductDto dto) {
    return ResponseEntity.status(HttpStatus.CREATED).body(service.add(dto, ownerId));
}
1Answers POST /products. No brackets, so it uses the class address as it is.
2Will send back one product, as JSON.
2Takes who is calling from the header the gateway attached. The caller cannot choose this.
3Takes the JSON that was sent and turns it into a ProductDto, checking the rules on it first.
4Calls the service, once, and answers 201 Created with whatever came back.

One line of real work. Everything else is labels describing what goes in and what comes out. Notice what is not there: no database, no price calculation, no check about who owns what, no error handling. All of that lives in the service.

Part 8

A template to copy

Replace Thing with whatever you are building, and delete the methods you do not need.

package com.shoppingcart.thing.controller;

import com.shoppingcart.thing.dto.ThingDto;
import com.shoppingcart.thing.service.ThingService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/things")
public class ThingController {

    private final ThingService service;

    public ThingController(ThingService service) {
        this.service = service;
    }

    // GET /things
    @GetMapping
    public ResponseEntity<List<ThingDto>> getAll() {
        return ResponseEntity.ok(service.getAll());
    }

    // GET /things/5
    @GetMapping("/{thingId}")
    public ResponseEntity<ThingDto> getById(@PathVariable Long thingId) {
        return ResponseEntity.ok(service.getById(thingId));
    }

    // POST /things
    @PostMapping
    public ResponseEntity<ThingDto> add(@RequestHeader("X-User-Id") Long userId,
                                        @Valid @RequestBody ThingDto dto) {
        return ResponseEntity.status(HttpStatus.CREATED).body(service.add(dto, userId));
    }

    // PUT /things/5
    @PutMapping("/{thingId}")
    public ResponseEntity<ThingDto> update(@PathVariable Long thingId,
                                           @RequestHeader("X-User-Id") Long userId,
                                           @Valid @RequestBody ThingDto dto) {
        return ResponseEntity.ok(service.update(thingId, dto, userId));
    }

    // DELETE /things/5
    @DeleteMapping("/{thingId}")
    public ResponseEntity<Void> delete(@PathVariable Long thingId,
                                       @RequestHeader("X-User-Id") Long userId) {
        service.delete(thingId, userId);
        return ResponseEntity.noContent().build();
    }
}

The imports matter. jakarta.validation.Valid, not javax: Spring Boot 3 renamed these, and most older tutorials online still show javax, which will not compile here.

Part 9

Mistakes to expect

What happensWhy
404 on an address you just wrote The class is missing @RestController, or the address does not match once you combine the class and method parts.
Validation never runs @Valid missing on the parameter.
The JSON arrives with every field empty @RequestBody missing, or the field names in the JSON do not match the DTO field names.
required request header X-User-Id is not present You called the service port directly instead of going through the gateway on 9090.
Two methods answer the same address Spring refuses to start and says the mapping is ambiguous. Two methods have the same label and the same brackets.
Returns text instead of JSON @Controller was used instead of @RestController.
The method never runs Wrong kind of label: sending POST to a method marked @GetMapping.

How to check a new endpoint quickly

Start the service, then open its own Swagger page in a browser, for example http://localhost:8083/swagger-ui.html. Every endpoint you have written appears in the list. If yours is not there, Spring never registered it, and the problem is in the labels, not in your logic.
