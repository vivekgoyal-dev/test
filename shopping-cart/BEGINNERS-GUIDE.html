Part 1

What we are building

Imagine a small online shop. Three kinds of people use it.

A customer

Signs up, looks at products, puts things in a basket, and places an order.

A shop owner

Signs up, adds the products they sell, and marks orders as shipped.

An admin

That is us. Can look at everything: all users, all products, all orders.

We are building only the back part of that shop. There are no screens, no buttons, no colours. There is no website to click on.

In plain words

A website has two halves. The front is what you see and click. The back is the part that actually remembers things, checks passwords, and does the work. We are building the back half only.

So instead of clicking a button, we send instructions using a tool called Postman. Think of Postman as a way to talk to the program directly, without a website in the middle.

That may feel strange at first. But it is completely normal at work: in a real team, one person builds the back half and another builds the screens. They are built separately and joined later.

Part 2

Java and Spring Boot

Java is a programming language. It is the language all our instructions are written in. Like any language, it has its own grammar and its own words.

Spring is a very large helper library for Java. Instead of writing everything yourself, Spring has already written the boring, repeated parts, and you use them.

Spring Boot is Spring made easy to start. It sets up sensible defaults so you can run a program straight away instead of spending a day on settings.

In plain words

Java is the language. Spring is a big box of ready-made parts. Spring Boot is that box, pre-arranged so you can start quickly.

You will write far less code than you expect. Most of the time you are telling Spring what you want, and Spring works out how.

What is Maven?

Our project uses many of these ready-made parts, and each part is a file that has to be downloaded from the internet. Maven is the tool that does this for you.

Every project folder has a file called pom.xml. That file is a shopping list. It says "I need Spring Boot, I need the MySQL driver, I need Lombok." Maven reads the list, downloads everything, and builds the program.

This is why the very first build is slow. Maven is downloading hundreds of files. The second time it is fast, because they are already on your computer.

Part 3

Why seven programs instead of one

We could have written this shop as one single program. Instead it is seven separate programs, each doing one job, all running at the same time.

Think of a real shop building. There is a billing counter, a stock room, a security guard at the door, and a reception desk. Each has one job. They are separate, but together they are one shop.

ProgramIts one job
auth-serviceSign up and log in. Keeps passwords.
profile-serviceRemembers a person's name, phone, birthday.
product-serviceThe list of things for sale.
cart-serviceWhat is currently in someone's basket.
order-serviceOrders that have been placed, and their status.
api-gatewayThe security guard at the front door.
discovery-serverThe internal phone directory.

Each one is a separate folder, with its own pom.xml, and each one is started separately. When they are all running, you have seven black windows open on your screen. That is normal and correct.

Why bother?

Because you can change the product list without touching the login code. And if the basket program crashes, people can still log in. In one big program, one mistake stops everything.

This style has a name: microservices. Micro means small, service means a program that does a job for others. Small programs, each doing one job.

The cost is that there are seven of everything: seven folders, seven settings files, seven windows. That is the trade. More pieces to start, but each piece is simple.

Part 4

How programs talk to each other: APIs

An API is just a list of things a program will do for you if you ask properly. Nothing more mysterious than that.

You ask by sending a request to an address, and the program sends back a response. Exactly like typing a web address into a browser, except the answer is data instead of a page.

An address looks like this:

http://localhost:9090/products
^              ^    ^
|              |    +--- which thing you want
|              +-------- which door (port number)
+----------------------- this computer

localhost means "this computer, right here". Because everything is running on your own laptop, every address starts that way.

The four kinds of request

Every request has a method, which says what kind of thing you want to do. There are four you will use:

MethodMeansExample
GETShow me somethingShow me all products
POSTCreate something newAdd a new product
PUTChange somethingChange the price
DELETERemove somethingDelete a product

So GET /products means "show me the products", and POST /products means "here is a new product, save it". Same address, different meaning, because the method is different.

What comes back

Every response has a status code: a three digit number saying how it went. You only need to know a handful.

CodeMeansWhat to do
200Fine, here is your answerNothing, it worked
201Created successfullyNothing, it worked
400You sent something wrongRead the message, fix what you sent
401I do not know who you areLog in, send your token
403I know you, but you are not allowedWrong role for this action
404That address does not existCheck the address for typos
500The program itself brokeLook at the black window for the error

The two most confusing ones

401 and 403 are different. 401 means you did not show your ticket. 403 means you showed a valid ticket, but it does not let you into this room.

404 is often just a typo. An extra space or an extra slash at the end of the address is enough to cause it.

Part 5

JSON, the format of the messages

When you send information to the program, or it sends some back, it is written in a format called JSON. It looks like this:

{
  "productName": "Wireless Mouse",
  "category": "electronics",
  "price": 1299
}

The rules are small:

  • Curly brackets { } wrap one thing.
  • Inside, you write "name": value pairs, separated by commas.
  • Text goes in double quotes. Numbers do not.
  • Square brackets [ ] mean a list of several things.

So this is a list of two products:

[
  { "productName": "Wireless Mouse", "price": 1299 },
  { "productName": "Keyboard",       "price": 2499 }
]

The most common beginner mistake: a comma after the last item, or a missing quote. JSON is strict. If you get a confusing error when sending something, check the commas and quotes first.

Part 6

Where the information is kept: the database

If the program only kept things in memory, everything would vanish when you close it. So information is written to a database, which keeps it on disk.

Ours is MySQL. It stores information in tables, which are very much like a spreadsheet: columns for the fields, one row per item.

product table

 productId | productName     | category    | price | ownerId
-----------+-----------------+-------------+-------+---------
     1     | Wireless Mouse  | electronics |  1299 |   19
     2     | Keyboard        | electronics |  2499 |   19

Why five databases?

Each service has its own separate database, named after it: shopcart_auth, shopcart_profile, shopcart_product, shopcart_cart, shopcart_order.

The rule is: a service may only touch its own database. The product service cannot read the orders table. If it wants order information, it has to ask the order service politely, through an API.

Why so strict?

Because it keeps the services genuinely separate. If everyone could read everyone's tables, changing one table would break four other programs, and you would be back to one big tangled program wearing five hats.

You never have to create the tables yourself. Spring reads your Java classes and creates the tables to match, the first time it runs. You only create the five empty databases.

Part 7

Login, and what a token actually is

When someone signs up, we save their email and password. But we never save the password as they typed it.

It is scrambled first, using something called BCrypt. The scrambling only works one way: you cannot turn the scrambled text back into the password. To check a login, we scramble what they just typed and compare the two scrambled versions.

Why it matters

If someone steals the database, they still do not have anyone's password. This is not optional in real work, it is the minimum standard.

The token

After a successful login, the program gives you a long piece of text called a token. It looks like nonsense:

eyJhbGciOiJIUzM4NCJ9.eyJzdWIiOiIxOSIsInJvbGUiOiJTSE9QT1dORVIifQ.J9y3abaul...

It is not nonsense. Inside, it says who you are and what role you have. It is also signed, like a signature on a document, so nobody can change it without the program noticing.

Think of a cinema ticket

You prove who you are once, at the counter, and you get a ticket. After that nobody asks for your ID again. You just show the ticket, and it says which screen you are allowed into.

Our token is that ticket. You log in once, then send the token with every later request. Ours expires after 24 hours, like a ticket for today's show only.

You send it in a header, which is extra information attached to a request:

Authorization: Bearer eyJhbGciOiJIUzM4NCJ9...

In Postman you do not type that by hand. Go to the Authorization tab, choose Bearer Token, and paste just the token. Postman writes the header for you.

Three things that cause a 401 even with a good token: pasting the quotes around it, pasting it with a line break in the middle, or typing the word Bearer into the box when Postman is already adding it.

Part 8

Three pieces with strange names

These three cause the most confusion, and all three are simple ideas with technical names.

The gateway: the guard at the door

You never talk to the seven programs directly. Everything you send goes to one address, the gateway, and it decides what happens next.

It does three things to every request:

  1. Checks your token is real and has not expired. If not: 401.
  2. Checks your role is allowed to do this. If not: 403.
  3. If both are fine, passes the request on to the right service.

Because the guard has already checked, the services behind it do not check tokens at all. They simply trust two notes the guard staples to the request: who the caller is, and what role they have.

Eureka: the phone directory

The gateway needs to pass requests to product-service. But how does it know where that is?

When each service starts, it phones a directory called Eureka and says "I am product-service, I am at this address." Later, the gateway asks Eureka "where is product-service?" and gets the address.

Why not just write the address down?

Because then every address is written in many places, and changing one means hunting through all of them. With a directory you use the name, and the address is looked up when needed.

This is why the phone directory has to be started first. If nobody is answering the phone, nobody can register.

Feign: asking another department

Sometimes one service needs something from another. When you add an item to your basket, the basket service does not know the price. It has to ask the product service.

Feign is a tool that makes this look like a normal method call. You describe the question you want to ask, and Feign writes all the messy network code for you.

ProductDto product = productClient.getProductById(8);

That single line quietly sends a request to another program, waits for the answer, and hands it back. It looks local. It is not.

Why the basket asks at all

Because a price sent by the customer cannot be trusted. If the basket accepted whatever price it was given, anyone could buy a laptop for one rupee. The price always comes from the product service, which is the only place that really knows it.

Part 9

Inside one service: the eight folders

Open any of the seven folders and you find the same eight folders inside. Once you understand one service, you understand all of them.

Think of a request arriving as a customer walking into an office. It passes through people in a fixed order:

controller — the receptionist

Takes the request at the door. Does no real work. Writes down what was asked and passes it to the right person. Then hands the answer back.

service — the person who does the work

All the actual thinking lives here. "Is this price valid?" "Does this person own this product?" Every rule in the project is in a service class.

repository — the filing clerk

The only one who touches the database. Fetches rows, saves rows. You write almost no code here: you write the method name and Spring writes the query.

model — the shape of a filing card

A Java class describing one thing stored in the database. A Product has a name, a category, a price. This becomes a table.

dto — the shape of a message

What goes out to the outside world, and what is accepted coming in. Deliberately not the same as the model.

exception — what to say when things go wrong

Turns a problem into a tidy message with the right status code, instead of a page of red error text.

config — settings and setup

Pieces that have to be prepared once when the program starts.

aop — the CCTV camera

Quietly writes a line in the log every time any method runs. Explained in a moment.

Why model and DTO are separate

This is the part people find fussy at first, and it has one very good reason.

The model for a user contains their password. If we sent the model straight back to whoever asked, we would be handing out passwords. So there is a second class, the DTO, which has all the same fields except the password.

In plain words

The model is what we keep. The DTO is what we are willing to show. They are usually similar, and the differences are where the important decisions live.

DTO stands for Data Transfer Object. The name tells you nothing useful. Just read it as "the version we send".

Part 10

Words you will see in the code

Things starting with @

Java code is full of words starting with @, like @Entity or @GetMapping. These are called annotations. An annotation is a label you stick on a class or a method, telling Spring how to treat it.

You are not calling anything. You are labelling something, and Spring reads the labels.

AnnotationWhat it says
@EntityThis class is a database table
@IdThis field is the unique number for each row
@RestControllerThis class receives web requests
@GetMapping("/products")Run this method for GET /products
@PostMappingSame, but for POST
@RequestBodyTake the JSON that was sent and turn it into an object
@ServiceThis class holds rules; Spring, please manage it
@ValidCheck the rules on this before running anything

Lombok

In Java, a class normally needs a getName() and setName() method for every single field. For a class with ten fields that is twenty boring methods.

Lombok writes them for you. You put @Data on the class and the methods appear when the code is compiled, without being in the file.

@Data
public class Product {
    private String productName;
    private double price;
}
// getProductName(), setProductName(), getPrice(), setPrice()
// all exist, even though you cannot see them

This causes a famous confusion. If Lombok is not set up in Eclipse, the editor cannot see those invisible methods, and shows hundreds of red errors like getPrice() is undefined even though the project builds fine.

The fix is a one-time setup: run java -jar lombok.jar, point it at your Eclipse folder, restart Eclipse.

Validation

We check what people send us before doing anything with it. The rules sit right next to the field they protect:

@NotBlank(message = "product name is required")
private String productName;

@Positive(message = "price must be greater than 0")
private double price;

If someone sends a blank name, they get a 400 back with that exact message. No rule in the rest of the code has to worry about it.

One catch: the rules only run if the method is marked @Valid. Without that word, the annotations sit there doing nothing at all.

AOP, the CCTV camera

We wanted a log line every time any method runs: what was called, how long it took, and whether it failed. Writing that inside every method would mean hundreds of copies of the same three lines.

AOP lets you write it once, in one small class, and say "apply this around every method in the controller and service folders". Nothing in the business code changes.

ProductController.addProduct called
ProductController.addProduct returned in 84ms
ProductServiceImpl.deleteProduct threw NotFoundException: no product 91

In plain words

A camera watching every room, installed once, rather than asking every person in the building to write their own diary.

AOP stands for Aspect Oriented Programming. Again, the name helps nobody. It means "behaviour added around your code from the outside".

One deliberate exception: the camera is switched off for login and sign-up, because their inputs contain the actual password, and passwords must never appear in a log file.

Part 11

Following one real request all the way through

Here is what actually happens when a customer adds a mouse to their basket. This is the whole system in one example.

Now the same thing in real requests you can copy into Postman.

The customer sends this

POST http://localhost:9090/cart/items
Authorization: Bearer eyJhbGciOiJIUzM4NCJ9...

{ "productId": 8, "quantity": 2, "price": 1 }

Notice they cheekily included "price": 1.

What comes back

{
  "userId": 20,
  "items": [
    { "productId": 8,
      "productName": "Wireless Mouse",
      "price": 1299.0,
      "quantity": 2,
      "lineTotal": 2598.0 }
  ],
  "totalPrice": 2598.0
}

The price is 1299, not 1. The basket asked the product service and ignored what the customer sent. That one detail is the difference between a working shop and a shop anyone can rob.

And notice something else: nowhere did the customer say who they were. There is no user id in the address or in the message. The gateway worked it out from the token and attached it. That is why one customer can never see another customer's basket.

Part 12

Running it yourself

Do these in order. The first time takes a while; after that it is quick.

1. Check you have Java

Open Command Prompt and type:

java -version

If you see a version number of 17 or higher, you are fine. If it says the command is not recognised, Java needs installing first.

2. Install Lombok into Eclipse

Only needed if you are using Eclipse. Find lombok.jar inside your .m2 folder, then:

java -jar lombok.jar

Click Install, point it at your Eclipse folder, restart Eclipse. Skip this and the editor will show hundreds of errors that are not real.

3. Create the five databases

Open MySQL Workbench and run:

CREATE DATABASE shopcart_auth;
CREATE DATABASE shopcart_profile;
CREATE DATABASE shopcart_product;
CREATE DATABASE shopcart_cart;
CREATE DATABASE shopcart_order;

They stay empty. The tables inside appear on their own the first time each service runs.

4. Tell the programs your MySQL password

setx DB_PASSWORD "your-mysql-password"

Then close that window and open a new one. This command only affects windows opened afterwards, which catches everybody out at least once.

5. Start the programs

From the project folder:

run-local.cmd

Seven windows open, one per program. Or start them yourself, one per window, with java -jar target\<name>-1.0.0.jar inside each folder.

The order matters. discovery-server first, wait until it is ready, then the five services, then api-gateway last.

6. Check they are all alive

Open http://localhost:8761 in a browser. You should see a list with six applications in it. If a name is missing, that program did not start: look at its window for red text.

A healthy window ends with a line like Started ProductServiceApplication in 5.1 seconds.

7. Try it

In a browser, http://localhost:9090/products should show [], an empty list. That means everything is connected. Then move to Postman for the rest.

Opening http://localhost:9090 on its own gives a 404. That is correct and not a fault. Nothing is set up at the plain address; you have to ask for something specific, like /products.

Part 13

When something breaks

Every one of these has happened to someone on this project already.

What you seeWhat it really means
Hundreds of red errors like getPrice() is undefined Lombok is not installed in Eclipse. Part 12, step 2.
Port 8080 was already in use Another program has that number. Change server.port in that service's application.yml to a free one.
Communications link failure MySQL is not running. Start the MySQL service.
Access denied for user Wrong MySQL password, or you did not open a new window after setx.
Unknown database shopcart_cart The five CREATE DATABASE lines were not all run.
503 Service Unavailable The program being asked for is not running, or has not registered yet. Wait 30 seconds and check port 8761.
401 on everything Token missing, expired after 24 hours, or pasted with a line break.
403 when it should work Wrong role, or a stray space or slash at the end of the address. Both look identical from outside.
The window flashes and closes instantly The program failed at startup. Run it from a terminal instead so the error stays on screen.

The habit worth building

When something fails, do not guess. The answer is almost always written in the black window of the program that failed. Read the first red line, not the last: the lines below it are usually just consequences.
