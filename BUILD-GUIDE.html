Before you start

Fifteen minutes of setup, then you never touch it again.

You are going to build a small e-commerce backend the way real systems are built: as five separate Spring Boot applications that find each other through a registry, rather than one big program. There is no website and no login. Every endpoint is driven from Swagger UI or Postman, which is exactly how a backend developer tests their own work before a frontend exists.

Build them in the order below. Each one runs and is testable on its own before you start the next, so you are never debugging five things at once.

In Eclipse: Window › Preferences › Java › Installed JREs. You need JDK 17 or newer selected. Spring Boot 3 will not start on Java 8 or 11.

File › New › Other and type spring. If Spring Starter Project appears, you are set. That wizard is Spring Initializr built into Eclipse.

If it is missing, install Spring Tools 4 from Help › Eclipse Marketplace and restart. Without it you can still follow along: generate each project at start.spring.io, unzip it, then File › Import › Maven › Existing Maven Projects.

3

Install Lombok into Eclipse

This one catches everyone. Lombok writes the getters and setters for you at compile time, and Eclipse needs a small agent installed before it can see them, otherwise your editor fills with red errors like getPrice() is undefined even though Maven builds fine.

Find lombok.jar in your Maven repository (~/.m2/repository/org/projectlombok/lombok/, any recent version), then run it and point it at your Eclipse install:

Click Install / Update, restart Eclipse. Do this once, before you write any code.

4

Know these two buttons

Run As › Spring Boot App starts a service. The Boot Dashboard (Window › Show View › Other › Boot Dashboard) starts and stops all of them from one panel. Worth opening now, you will use it constantly by phase 6.

Keep every service running once you start it. By phase 5 the services call each other, and a stopped service looks exactly like a bug in the code you just wrote.

The registry

One tiny project whose only job is to know where everything else lives.

Five services need to find each other without anyone hardcoding localhost:9082 all over the code. Eureka is the phone book: each service registers its name on startup, and a service that wants product-service asks the registry rather than remembering a port.

Build it first, because everything else registers with it.

product-service

The catalog. No dependencies on anything, so it is the right place to learn the shape every service follows.

Every service you build has the same five layers, and once you have typed them once the other four are variations:

entitythe table
dtowhat the API sends and accepts
repositorythe queries
service + serviceImplthe rules
resourcethe HTTP endpoints

The DTO is worth understanding rather than copying blindly. It is a separate class from the entity so that what you store and what you expose can differ. You will see exactly why in phase 3, where the DTO is how a password gets accepted on the way in and never sent back out.

profile-service

Customers, merchants and delivery agents. Same five layers, one new idea.

The new idea is that the DTO earns its keep. UserProfile stores a password; UserProfileDto marks that field WRITE_ONLY, so it is accepted when someone registers and silently dropped from every response. Storing something you never return is not possible with one shared class.

The profileId this service hands out is the customer id used everywhere else: it becomes their cart id and their wallet id. Note the first one you create.

wallet-service

Money. The first service where being sloppy has consequences.

Two rules make this service trustworthy, and both are worth understanding before you type them.

The balance never moves without a statement row. Every deposit and every payment writes its own row saying what happened, when, and for which order. That is why record(...) is called inside both money methods and never skipped.

A payment that cannot be afforded is refused before anything changes. The balance check happens first; if it fails, nothing is written at all.

cart-service

The first service that calls another one. This is where it becomes a microservice system.

A cart has to know what a Kindle costs. It does not store prices and it does not trust the caller to send one. It asks product-service. Two pieces make that work:

@LoadBalanced RestTemplate is a bean in the main class. It lets you write a URL with a service name where the host would normally go: http://product-service/products/name/.... The registry from phase 1 turns that name into a real address at call time, so nothing in your code knows or cares which port product-service is on.

The price is overwritten, always. Look at save(...): whatever price arrives in the request is discarded and replaced with the one product-service returned. Trusting a client-supplied price is how shopping carts get exploited.

6

order-service

Checkout, both ways. The hardest and most interesting service.

This service turns a cart into orders, and it can take the money. Three decisions inside it are worth your attention, because they are the difference between a demo and something you would defend in a review.

One order row per cart line. An Orders row holds one product and one quantity, so a cart with three products becomes three orders that share a date and an address. That is why both checkout methods return a list.

A failed payment must leave nothing behind. onlinePayment writes the orders first (a payment needs a real order id to reference), then debits the wallet. Both happen inside one @Transactional method, so when the wallet refuses, the exception rolls the orders back and the customer is left with neither an order nor a charge.

It keeps its own copy of Address and Product. Order-service does not reach into another service's database, it stores what it needs. An invoice has to still be correct in five years even if the product is delisted and the price changes.

CheckpointThe whole system works

All six applications running. Use the Boot Dashboard to confirm. Then, on Swagger 9084:

  1. POST /orders/address stores a delivery address for customer 1. Checkout fails without one, on purpose.
  2. GET /carts/1 on port 9083, copy the whole response
  3. POST /orders/place takes it as the body. Cash on delivery. You get an order back.
  4. POST /orders/onlinePayment takes the same body. Check the wallet balance on 9085: it dropped by the order total, and GET /wallets/1/statements shows a Withdraw carrying that order id.
  5. GET /orders/customer/1 returns both orders, one marked Cash on delivery and one Wallet.
  6. PUT /orders/1/status?status=Shipped is the merchant's side.

Then the test that proves the design. Drain the wallet with PUT /wallets/1/pay until almost nothing is left, count your orders with GET /orders, and run POST /orders/onlinePayment again. You should get 400, and GET /orders must return the same count as before. If a phantom order survived a failed payment, the @Transactional on onlinePayment is missing or the exception is being swallowed.

7

When it is all running

What to check, what breaks, and what is deliberately missing.

Start them in this order

discovery-server first, always. Then the other five in any order. In the Boot Dashboard you can select all five and start them together once Eureka is up.

The four errors you will actually hit

Port 9082 was already in useSomething else has the port, or a previous run never died. Stop it in the Boot Dashboard, or change server.port in that service's application.yml.
getPrice() is undefinedLombok is not installed into Eclipse. Phase 0, step 3, and restart Eclipse afterwards.
Connection refused / 503 on a cart or checkout callThe service being called is not running, or has not registered yet. Check the dashboard; registration takes about 30 seconds.
Table not found, or old data reappearingH2 is writing to a file under the service's data/ folder. Delete that folder and restart for a clean database.

Look inside the database

Each service exposes an H2 console at localhost:9082/h2-console for products. JDBC URL jdbc:h2:file:./data/productdb, user sa, no password. Useful when an endpoint returns something you did not expect and you want to see what was actually stored.

What this build deliberately does not do

Worth knowing before someone asks you in a review:

  • The cart is not emptied after checkout, so posting the same cart twice places the order twice.
  • There is no authentication, so any caller can act as any customer id. Real systems put a token check in front of every endpoint.
  • Cancelling an order does not refund the wallet, the status changes and the money stays spent.
  • Ratings and reviews can be stored but there is no endpoint to add a single review.

Each one is a good next exercise, and each is a real conversation about where the responsibility belongs: should order-service reach over and empty the cart, or should cart-service listen for an order being placed?

Every code block on this page is taken verbatim from a build that runs: all six services start, register with Eureka, and pass an end-to-end test from sign-up through wallet checkout, including the rolled-back payment.
